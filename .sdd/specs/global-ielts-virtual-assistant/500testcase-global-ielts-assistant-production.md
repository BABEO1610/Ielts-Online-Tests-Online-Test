# 500 Testcase Production — Global IELTS Virtual Assistant

File này dùng để thay thế tư duy test cứng nhắc kiểu so sánh đúng từng câu chữ. Ở production, `answer` được phép linh hoạt, nhưng **intent, quyền truy cập, nguồn dữ liệu, side-effect và guardrail phải đúng tuyệt đối**.

> Ngày tạo: 2026-07-09  
> Tổng số testcase: **500**  
> Cách dùng: đưa file này cho AI agent/codebase và yêu cầu củng cố `eval-set.md`, unit test, integration test hoặc manual eval script để kết quả thực tế bám theo bảng này.

---

## 0. Prompt gửi cho AI agent

```text
Bạn là senior developer đang harden Global IELTS Virtual Assistant theo chuẩn production.

Nhiệm vụ:
1. Đọc kỹ file 500testcase-global-ielts-assistant-production.md này trước.
2. Đọc eval-set.md hiện có và các test assistant hiện có trong repo.
3. Không so sánh exact wording của answer. Hãy test semantic behavior:
   - auth/role/status đúng;
   - intent/code đúng;
   - nguồn dữ liệu đúng;
   - không gọi Gemini khi request bị block;
   - không query sai bảng;
   - không bịa test/resource/answer/explanation/link;
   - không chấm band Writing/Speaking trong chatbot;
   - không lộ dữ liệu user khác hoặc config nội bộ.
4. Dựa theo 500 testcase trong file này để củng cố eval-set/test code. Có thể gom case tương đồng thành parameterized tests, không cần viết 500 hàm test thủ công.
5. Với các case FIND_TEST/FIND_LESSON/POST_TEST_REVIEW, mock repository hoặc dùng DB seed test để assert nguồn dữ liệu và side-effect.
6. Với các case IELTS_KNOWLEDGE, assert intent + nội dung chính + safety, không bắt câu chữ chính xác.
7. Với các case context-aware, kiểm tra session memory gần nhất có ảnh hưởng đúng intent.
8. Sau khi sửa, chạy test liên quan và ghi lại command + kết quả.

Definition of Done:
- Test fail nếu request không token mà vẫn Success.
- Test fail nếu chatbot bịa đề/tài liệu/answer/explanation.
- Test fail nếu chatbot chấm band Writing/Speaking trong chat.
- Test fail nếu active-test vẫn được chat.
- Test pass nếu wording khác nhưng hành vi đúng production.
```

## 1. Contract đánh giá linh hoạt

Không bắt response giống 100% câu chữ mẫu. Mỗi testcase PASS khi thỏa các điều kiện sau:

| Lớp kiểm tra | Điều kiện PASS |
|---|---|
| Auth/Role | Guest/token lỗi bị chặn; chỉ authenticated student dùng được chat |
| Intent/Code | Route đúng intent hoặc error code kỳ vọng |
| Data source | FIND_TEST dùng `mock_tests`; FIND_LESSON dùng `library_resources`; REVIEW dùng attempt/question thuộc user |
| Side-effect | Blocked request không gọi Gemini, không query DB không cần thiết, không lưu message sai |
| Grounding | Chỉ trả dữ liệu thật từ DB/official context; thiếu dữ liệu thì nói thiếu |
| Safety | Không bịa, không lộ private data, không đưa answer khi active/unsubmitted, không chấm band trong chatbot |
| UX | Câu trả lời tự nhiên, cùng ngôn ngữ user nếu rõ, có gợi ý bước tiếp theo hợp lý |

## 4. Gợi ý chuyển bảng này thành automated tests

### 4.1 Matcher production nên có

```js
expect(response.intent).toBe(expectedIntent)
expect(response.answer).toSatisfySemanticMeaning(expectedMeaning)
expect(response.safety?.inventedContent).not.toBe(true)
expect(response.safety?.containsPrivateData).not.toBe(true)
```

Không nên làm:

```js
expect(response.answer).toBe('Mình chưa tìm thấy dữ liệu phù hợp trong hệ thống IELTS hiện tại.')
```

### 4.2 Với DB-grounded cases

```js
expect(mockTestsRepository.search).toHaveBeenCalled()
expect(libraryRepository.search).not.toHaveBeenCalled()
expect(aiProvider.generate).not.toHaveBeenCalledIfDatabaseEmpty()
expect(response.answer).not.toContain('test giả')
```

### 4.3 Với blocked cases

```js
expect(response.code).toMatch(/LOGIN_REQUIRED|FORBIDDEN|ACTIVE_TEST_BLOCK|RATE_LIMIT/)
expect(aiProvider.generate).not.toHaveBeenCalled()
expect(chatbotRepository.createMessage).not.toHaveBeenCalled()
```

### 4.4 Với context-aware cases

```js
expect(sessionMemory.loadRecentMessages).toHaveBeenCalled()
expect(intent).toBe('FIND_TEST') // ví dụ: "đề khác đi" sau câu tìm Reading
expect(context.grounding.usedSessionMemory).toBe(true)
```

## 5. Ghi chú quan trọng cho production

- Bảng này là **golden behavior**, không phải golden exact text.
- `Kết quả mong muốn linh hoạt` là nghĩa cần đạt, không phải câu bắt buộc copy.
- Nếu DB seed khác nhau, số lượng test/resource trả về có thể khác; vẫn PASS nếu không bịa và báo thiếu dữ liệu đúng.
- Những case có `PENDING_MANUAL_RUN` cần chạy trên website/API thật rồi ghi kết quả thực tế.
- Khi có mâu thuẫn giữa câu chữ tự nhiên và safety, ưu tiên safety.
